EpicSpine

A repository's living memory, written as a tree of short markdown files. Any agent, or you, can drop in cold, read about a hundred lines, and know what we're trying to achieve, where it stands, what's next, and where to look for more. Then it pulls in extra context only as it needs it.

The problem it solves

Agents start every session with no memory. Without a shared record they redo work, contradict past decisions, and lose track of what "done" means.

The idea

Put intent, facts, state, decisions and learnings in one place per goal, in plain markdown that lives in git, next to the code.

The promise

A fresh agent binds in three hops: repo entry, root spine, then the spine for its task. It knows how to keep going without asking you where things are.

1 · Three layers: say each rule once, at the right level

machine

The skill (EpicSpine itself)

Behaviours every agent follows everywhere: bind, place the ask in the tree, dispatch workers, verify, integrate, record, learn. Hooks inject these each session, and the dispatcher picks worker seats.

repo

AGENTS.md + root spine

Values specific to this repo: where the root is, how work reaches main (Integration policy, Deploy gate), worker profile, repo-wide learnings.

spine

Each goal's spine

Only what belongs to this goal: its intent, state, steps, decisions and exceptions. It never restates the defaults above.

2 · Spines form a tree of goals (the epic log)

 ├─ EPIC-3 Epic logactive
 │   └─ E3-1 … E3-5: checkboxes = smaller goals
 └─ EPIC-4 Doctrine 2ready

This repo's real tree, today.

Root: states the repo's purpose. Everything hangs from it.

Epic (goal): a measurable objective worked over several pushes. It gets its own markdown file with a code (EPIC-<n>: name) and is linked from its parent.

Smaller goals: progress inside one epic is a checkbox line in that epic, not a new file. Choosing between the two is a judgment call.

Links both ways: the child names its parent (Parent spine:), and the parent lists the child in its Spine Map. A commit check keeps the two in agreement. spines.py --json returns the whole tree to any reader, including the agent_team console.

3 · Inside one spine

Five kinds of information, each in a fixed place, so humans and machines know where to look: intentfactsstatelearningslinks

Header linksfactsIdentity and place in the tree: Spine ID, root, parent, integration branch, doctrine version.
Goal (Mission) intentIn plain words: what changes, and why it matters. Readable without knowing the code.
Serves intentlinksHow this goal serves its parent's goal, so the tree reads as one story. (Doctrine 2, being defined)
Current State stateThe snapshot, about ten lines: owner, status, last attempt, result, evidence, waiting on, approved work, next action, verified at. Overwritten each step; history lives in git.
Definition of Done ("Done means") intentstate2–5 measurable outcomes as checkboxes - [ ] ID text, ticked only with evidence. Outcomes, not a copy of the ticket list.
Issue Ledger statelinksThe steps toward done: one row each, with owner, status, dependency, branch, evidence and next action.
Decisions factsWhat is settled and why, including what was tried and rejected, so no one reopens it by accident.
Operating Learnings learningsRules learned from you ("always / never…"), one line each, stored in the deepest spine they apply to.
Spine Map linksIts children: status, health and next action, plus (Doctrine 2) one sentence on what each child contributes.

Green bar = exists today. Amber = being defined in EPIC-4.

4 · How an agent uses it: read little, then pull what it needs

1 · AGENTS.md
Names the root and the repo rules
→
2 · Root spine
Current State + learnings
→
3 · Parent chain
Follows the active branch down
→
4 · Its spine
Goal, state, next action
→
5 · On demand
Decisions, linked docs, tickets, code

Everything after step 4 is pulled only when the task needs it. A spine is a map, not an encyclopedia.

5 · The maintenance loop the agent runs

Bind
Name role and learnings
→
Place
Put the ask in the tree: existing goal or new leaf
→
Dispatch
Manager hands work to workers; it never implements
→
Verify & integrate
Check diff and tests, merge to main with history
→
Record
Update Current State, ledger, boxes; commit and push
→
Learn
Your always/never becomes a learning line

Pushing after each step is what lets agents on other machines (VPS, laptop) see the same truth.

6 · Spine vs tickets

SpineTicket (ledger row, optionally a GitHub issue)
AnswersWhy, what outcome, how the pieces fit, where we are, what's nextHow to do one concrete step
HoldsIntent, state snapshot, decisions, learnings, linksCode paths, logs, blockers, review discussion
LifespanAs long as the goalOne step
RuleDeep discussion stays in the ticket; only the durable consequence (changed intent, state or decision) is written back into the spine.
